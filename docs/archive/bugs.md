## Completed/Resolved Bugs

### [Fixed] Clear All crashed (TypeError) when the queue emptied to zero without a session loaded
* **Symptom:** `Uncaught (in promise) TypeError: Cannot read properties of null (reading 'path')` at `main.js:661`, via `renderMasterList` → `replaceScannedDemos` → the Clear All Anyway button handler. Reproduced with a plain "+ Add Demo Files" scan (no Load Session) across several demo counts, always Clear All'ing the queue down to exactly 0.
* **Root Cause:** A second bug in the same area as the stack-overflow fix directly above, exposed once that fix started working correctly. `renderMasterList()`'s empty-queue notification calls whatever `onSelectDemo` callback is currently registered with `(null, null)`. Load Session's callback (`main.js:465`) already handled a null demo fine — that's the one the recursion bug exercised. The *other* registration, from a plain folder/file scan (`main.js:655`), didn't: it unconditionally read `demo.path` to update the View Telemetry button and kick off `analyzeDemo(demo.path)`, with no null guard, since nothing had previously emptied the queue to zero via that code path.
* **Resolution:** Added an explicit `if (!demo)` early-return to that callback — resets the telemetry button/panel instead of dereferencing a demo that isn't there. Also audited the rest of that render chain (`renderDetailView`, `updatePreviewButtonStates`) and confirmed they were already null-safe; this was the one unguarded spot.

### [Fixed] Every `confirm()` dialog in the app never actually blocked on the user's choice
* **Symptom:** Surfaced while chasing the Clear All stack-overflow bug above — after that fix, Clear All's plain-`confirm()` path (untracked demos, no modal) still logged an uncaught console error, `dialog.confirm not allowed. Command not found`, and the demos got removed regardless of what the user would have clicked. Same underlying `confirm()` call pattern is used by Demo Auditor's "delete duplicate files" and Capture Studio's "delete orphaned preview demos" — both pre-existing, from before this session, not new code.
* **Root Cause:** Two stacked issues. (1) Tauri's global `window.confirm`/`window.alert` interception requires the `dialog:allow-confirm`/`dialog:allow-ask` permissions specifically — `dialog:default` (already granted) only bundles `allow-message`/`allow-save`/`allow-open`, so the global override always failed permission checks. (2) Even fixing that wouldn't have been enough: Tauri's `window.confirm` override is asynchronous (returns a Promise), but every call site in this codebase used the synchronous browser pattern (`if (!confirm(...))`). A Promise is truthy, so `!confirm(...)` was always `false` — the code always proceeded as if the user clicked OK, regardless of whether a dialog even appeared. The permission failure just made this visible (an uncaught rejected-promise error logged after the fact, too late to matter); without it, the app would have silently skipped every confirmation entirely.
* **Resolution:** Stopped relying on the global `window.confirm` altogether. Every call site (`main.js` ×2 — Clear Selected/Clear All, `master_pane.js`'s row-delete fallback, `auditor_pane.js`'s duplicate-file delete, `capture_pane.js`'s orphaned-preview delete) now imports the explicit `confirm()` from `@tauri-apps/plugin-dialog` — a proper `async function` returning `Promise<boolean>` — and awaits it (`if (!(await confirm(...)))`). That function routes through the plugin's `message` command, already covered by the existing `dialog:default` permission, so no capability changes were needed in the end.

### [Fixed] Clear All crashed with a stack overflow when it emptied the queue after a session was loaded
* **Symptom:** Clicking "Clear All Anyway" (or plain Clear All with nothing tracked) silently produced no success toast and stopped logging to `crash_log.md` mid-session, with no visible error in the app itself — devtools console showed `Uncaught (in promise) RangeError: Maximum call stack size exceeded`.
* **Root Cause:** `master_pane.js`'s `renderMasterList()` calls `currentOnSelectDemo(null, null)` whenever the queue is empty, to clear the detail view. After Load Session, that callback (`main.js`) calls `renderDetailView(null, null)`, which (via `updatePreviewButtonStates`) fires `detail_pane.js`'s `onSelectionChange` callback — which itself calls `renderMasterList()` again. With the queue still empty, that re-entered the same "notify empty" branch, calling `currentOnSelectDemo(null, null)` again, forever. Only reachable when a session had been loaded (registering that specific callback) *and* an action emptied the queue to exactly zero — Clear All (2026-08-19) was the first action that could do both at once; Clear Untracked/Selected never fully hit zero in prior testing.
* **Resolution:** `renderMasterList()` now only notifies `currentOnSelectDemo(null, null)` on the *transition* into an empty queue (tracked via a `wasEmptyQueue` flag), not on every re-render of an already-empty one — breaking the recursive cascade at its single re-entry point.

### [Fixed/Mitigated] All injected commands collapse to Tick 0 / Early Execution
* **Symptom:** Fast-forward and capture commands anchored at frame 0, or executed minutes too early, causing missed highlights and duplicated clips.
* **Root Cause:** A combination of array-truncation in the scanner (stopping at `type_byte == 5`) and a severe domain mismatch in the patcher loop. The patcher was evaluating scheduled gameplay ticks against `frame_counter` (the raw binary packet index), which grew exponentially faster than the actual game time.
* **Resolution:** Replaced raw float-time lookups with direct scanner indices, implemented mathematical fallbacks for truncated arrays in `find_tick_backwards`, and normalized the patcher loop to evaluate against `current_playback_tick` (calculated via `file_tick - base_tick`).

### [Fixed/Mitigated] svc_bad (SZ_GetSpace overflow) Crash During Demo Fast-Forward
* **Symptom:** The GoldSrc engine (`hl.exe`) would deterministically crash with a `svc_bad` error when attempting to fast-forward (`host_framerate`) through a demo after executing a `mirv_recordmovie` cycle.
* **Root Cause:** A binary formatting violation in the stream patcher (`native/src/patch/engine.rs`). The patcher was injecting director event `BOOKMARK` frames *interleaved inside* the payload of original `NetworkMessage` frames. The engine read the original frame header, expected gameplay data, but read the injected bookmark bytes instead. It interpreted those bytes as a 32-bit packet length, resulting in a phantom ~2.9 Gigabyte packet that instantly overflowed the `netchan` buffer.
* **Resolution:** Restructured the `engine.rs` patcher loop. It now buffers the `info_block`, injects pending bookmarks as complete, standalone frames *first*, and then writes the original network frame header and payload to keep the binary stream 100% aligned.
* **Resolution Notes:** Hard-clamped `fast_forward_speed` to 0.05 and implemented 3-frame command redundancy with `clear;` prefix to ensure state synchronization during high-density network spikes.
* **Not to be confused with the residual drip (2026-08-26):** `qconsole.log` still shows a handful of `SZ_GetSpace: overflow on netchan->message` lines per capture, with no crash. That is a different thing and is benign — see `docs/goldsrc_dod_quirks.md`. Measured across 34 sessions in one accumulated log it holds at ~1 per 60,000 frame records regardless of era, including sessions predating the decal flush; six of eight in the audited run landed mid-fast-forward nowhere near an injection. The crash above was deterministic and traced to a malformed stream; this one tracks playback length only. Check the per-session rate against an older session before opening an investigation.

### [Fixed] Batch Capture Failed Every Time: "Failed to open source demo for copy"
* **Symptom:** Clicking Start Capture Batch always failed immediately, logging `Failed to open source demo for copy: The system cannot find the file specified. (os error 2)` for every job in the batch, right after the drive-pool junctions were created.
* **Root Cause:** `build_batch_queue()` (`native/src/patch/builder.rs`) only ever *planned* each patched demo — its output path, drive routing, scheduled console commands — it never called `StreamPatcher::patch()` to actually write the patched bytes to disk. `capture_manager.rs` handed that job list straight to the capture engine (`native/src/capture_engine.rs`), which assumes `patched_demo_path` already exists and just tries to copy it into `dod/`. Only the separate Preview pathway (`launch_demo_preview`/`generate_all_previews`) ever called `StreamPatcher::patch()`; the batch-capture path never got the equivalent step during the Tauri port. A stale comment in `builder.rs` references "the inline patch_worker in `capture/select.rs`," a module that doesn't exist anywhere in this codebase — evidently a step the old pre-Tauri egui app had that was never carried over.
* **Resolution:** Added the missing patch loop in `capture_manager.rs`, right after `build_batch_queue()` returns and before jobs are handed to the capture engine — one `StreamPatcher::patch()` call per job, with a cancel-token check and a `capture_status` progress event between jobs (same event shape the frontend's progress bar/status text already renders, so no frontend changes were needed).

### [Fixed] Highlight Table & Master Queue Mixed Kills From Every Player in the Match
* **Symptom:** One demo in the Master Queue showed 130 highlights while its counterpart from the same match showed 14; the Highlight Details table's weapon-chain column sometimes mixed weapons from both teams within a single "streak" row.
* **Root Cause:** The POV filter in `detail_pane.js` (and, downstream, `master_pane.js`) gated on `demo.is_pov`, treating `false` as "no single recording player, show everyone." `is_pov` actually reflects whether the demo contains *any* `SvcHltv`/`SvcDirector` network message anywhere in the file — server-broadcast messages that also land in an ordinary player-recorded demo whenever an HLTV caster is merely spectating the live match, not just true HLTV proxy recordings (which are already rejected earlier in `scan_demo_for_highlights` and never reach this code at all). One half of a match had the HLTV feed live, the other didn't, so the exact same recording setup produced different `is_pov` values between the two files, and the demo where it read `false` leaked every other player's kill streaks into what should have been a single player's highlight list.
* **Resolution:** Gate on whether `local_player_index` actually resolved (`Some`/`None`) instead of on `is_pov`. Since true HLTV proxies are already filtered out before that field is ever computed, `None` reliably means "no resolvable owner"; `is_pov` never did. Fixed in `detail_pane.js`'s row filter and a new `recordingPlayerStreaks()` helper in `master_pane.js`.

### [Fixed] Disk Estimate, Capture Payload, and Timeline All Over-Counted Unselected Highlights
* **Symptom:** The pre-flight disk-space estimate was inflated for demos never opened in the Highlight Details view; the killstreak timeline canvas painted highlights green ("selected") even when nothing was checked in the Sel column.
* **Root Cause:** `streak.selected` is `undefined` until a row is actually rendered in the Highlight Details table, which sets it to `false` on first render (opt-in default — the checkbox itself renders unchecked for `undefined`). Three call sites instead treated `undefined` as *selected* (`selected === true || selected === undefined`): `computeRequiredCaptureBytes` (disk estimator), `renderTimeline`'s selection-color logic, and — most seriously — `buildCapturePayload`, the function that actually decides what gets captured. That last one meant clicking Start Capture Batch on a demo that had never been opened in the detail view would have captured every highlight from every player in it, not just what was checked.
* **Resolution:** All three now require `selected === true`. `undefined` correctly covers both "demo never opened" and "streak belongs to a non-recording player, never even rendered as a checkable row" (see the POV-filter bug above) — neither should ever be billed or captured.
