# VEGAS bridge and MCP server (R&D, #1050)

Lets Claude (or any script) drive VEGAS Pro 21: open or start a project, put clips on the timeline, set event speed, add Media FX, Event FX, Track FX or Video Output FX with presets, parameters and keyframes, read and set Pan/Crop, Track Motion, fades and transitions, markers, envelopes and event groups, make one change to many events at once, compare two projects, render a range to a file, save to a new path. Not built by CI or shipped with Studio.

Two parts:

- **`extension/`**: a VEGAS application extension (`DodStudioVegasBridge.dll`, C# against VEGAS's own `ScriptPortal.Vegas.dll`). VEGAS loads it into every VEGAS, but it listens only in a VEGAS started for it (see Safety), on the named pipe `\\.\pipe\dodstudio-vegas-<pid>` (current user only), for one JSON command per line, and runs each on VEGAS's UI thread inside an undo block, so Edit > Undo takes back one call.
- **`mcp/vegas_mcp.py`**: an MCP server (stdio, Python standard library only). Its `launch` tool starts its own VEGAS beside the user's, on a hidden desktop, and the other tools go to that VEGAS's pipe. `mcp/vegas_instances.py` starts, finds and ends those VEGAS processes, `mcp/desktops.py` makes the hidden desktop and starts VEGAS on it, and `mcp/bridge_pipe.py` is one pipe connection with a time limit on each call.

From a shell:

    python vegas_mcp.py launch [work-folder]              # start a bridge VEGAS (hidden, runs until end); prints its pid
    python vegas_mcp.py call --pid N <cmd> [json-args]    # one command (in PowerShell 5.1, pass the JSON from a variable or file)
    python vegas_mcp.py instances                         # every VEGAS, and which have a bridge
    python vegas_mcp.py end <pid>                         # end it and remove its autosave

Tests that need no VEGAS: `python -I -m unittest discover -s vegas-mcp/mcp -p "test_*.py"` (not run by CI).

## Install (no admin)

    powershell -ExecutionPolicy Bypass -File vegas-mcp\build.ps1 -Install

builds with the `csc.exe` that ships with .NET Framework 4.x and copies the DLL to `%APPDATA%\VEGAS Pro\21.0\Application Extensions`. In a VEGAS you start yourself, **Tools > Extensions** shows "DoD Studio bridge (off in this VEGAS)". `-Uninstall` removes it. On a PC that enforces WDAC it is signed with the `LocalRustDev` certificate when the user has one.

Register the MCP server with Claude Code (the user does this, not an agent), with the work folder the bridge may write in:

    claude mcp add vegas -e DODSTUDIO_VEGAS_ROOT=D:\some-test-folder\vegas -- python C:\path\to\dod-studio\vegas-mcp\mcp\vegas_mcp.py

Without `DODSTUDIO_VEGAS_ROOT` the work folder is `%TEMP%\dodstudio-vegas`; `launch` takes `work_folder` too. `DODSTUDIO_VEGAS_EXE` points at another `vegas210.exe`.

## Tools

| Tool | What it does |
|---|---|
| `launch`, `end` | Start a bridge VEGAS (beside the user's, on a hidden desktop; later tools go to it); end one by PID and remove its autosave, also while a call to it is stuck |
| `instances`, `use` | Every VEGAS, which have a bridge, which is busy with a call past its time limit; send later tools to another bridge VEGAS |
| `ping`, `project_info` | Versions, pid, work folder, dialogs answered; the open project's settings, tracks, events (time, speed, media offset, FX with parameter values; mute, locked, group and loop off only when set) and media pool. `detail: true` adds fades, snap offsets, track FX and compositing, envelope and keyframe counts, Video Output FX, markers, regions and event groups |
| `new_project`, `open_project` | Start a project (size, fps, pixel format) or open a `.veg` (one outside the work folder is copied in and the copy opened). Both refuse to drop unsaved changes unless `discard_changes` |
| `import_edl` | Open an EDL Text File (Studio's Export VEGAS EDL or Export Project to VEGAS) the way VEGAS does, as a new project; then size/fps and Select None (for the nameplate script). Reports how many events are offline |
| `save_as` | Save to a **new** `.veg` path. Overwrites only a file this bridge session saved, with `overwrite` |
| `add_media`, `set_event` | Put a file or subclip on the timeline (a new track goes after the existing ones, so no index moves; the reply gives its index); change an event's speed (`playback_rate` 0.2 = 5x slow; the media second it starts at stays), start, length, offset (media seconds at any speed), resample, mute, locked, loop, snap offset |
| `create_subclip` | A subclip of a file (it has its own Media FX chain) |
| `list_effects`, `add_effect`, `set_effect_params` | Find video FX, each once with the folders VEGAS lists it under (`details` adds its presets and OFX parameters: default, range, choices); add one to an event's, a media's, a video track's or the Video Output FX chain (`target`); apply a `preset` by name and set OFX parameters by name or label (points `[x, y]`, colours `[r, g, b, a]`) |
| `list_presets`, `read_preset` | An effect's or transition's presets (VEGAS's and the user's saved ones, in one list); what a preset sets, beside the defaults, without changing the project |
| `apply_to_events` | One change to every event a filter picks (track, time range, media, name, selected, type, or `all`), in one undo step: `set_event` fields or `shift`, `add_effect` / `set_effect` / `remove_effect` (Event FX or Media FX), `pan_crop`, `fade_in`, `fade_out`; returns what changed where and what was skipped |
| `compare_projects` | What differs between two `.veg` files, or the open project and one: settings, tracks, events added/removed/moved/changed (speed, offset, fades, FX parameters and keyframes, Pan/Crop, envelopes), Track Motion, Video Output FX, markers, Media FX; files read from copies, the open project reopened after |
| `get_keyframes`, `set_keyframes` | OFX parameter keyframes (time, value, interpolation) on any of those chains: replace, add or clear. Times are the chain's own: Event FX from the event's start (whatever its speed or offset), Media FX from the media's start, Track and Output FX from the project's start |
| `get_pan_crop`, `set_pan_crop` | A video event's Pan/Crop keyframes: the shown box in the source media's pixels (y down), centre, zoom, rotation (degrees), smoothness, interpolation; `zoom` and `pan` shortcuts do a whole move in one call |
| `get_track_motion`, `set_track_motion` | A video track's Track Motion keyframes (project pixels from the frame's centre, y up; size; rotation in degrees), and its 2D shadow and glow |
| `list_transitions`, `set_fade`, `crossfade` | Find transitions; an event's fade in or out (length, curve, a transition with preset and OFX params); a crossfade with the event before it, its start moved to make the overlap with its picture kept in place |
| `get_markers`, `set_markers` | Markers, regions and command markers; add, move, rename and delete in one call, every index from before the call |
| `get_envelopes`, `set_envelope` | Track envelopes (Volume, Pan, Composite level, Fade to Color, Mute) and a video event's Velocity: points with curves; replace, add or remove |
| `group_events` | Group events so they move together, or ungroup them |
| `blend_by_speed` | Frame Blend (#1051) that follows each event's speed, see below |
| `list_render_templates`, `render` | Find templates; render a range to a new file (never overwrites); `files` lists what was written, an Image Sequence's numbered files too |
| `snapshot` | See the project at a time (or up to 10 `times`): the composited frame at Best quality and full size, saved as a PNG under `<work folder>\snapshots` (a fresh name each time) and returned inline as an image, so Claude can check its own edits. `width` scales it down (default 1280, 0 = full size, never up). Leaves the cursor, preview settings and project as they were, see below |
| `run_script` | Run a C# VEGAS script from the work folder for anything else; compiled first as VEGAS compiles it (C# 5, no System.Core), so a compile error comes back instead of leaving a box open |

Every reply carries `dialogs` when VEGAS raised any during the call, with how each was answered, and `earlier_call` once a call that ran past its time limit has finished.

Every bridge tool takes `timeout_seconds`: how long the server waits for VEGAS. The default is 120 s, 600 s for `open_project` and `import_edl` (at least `wait_seconds` + 60), and an hour for `render`; one over a week is cut to a week, and infinity or NaN is refused. Past it the call is an error that names the command and the dialog-like windows open in that VEGAS, and the VEGAS is marked busy: a later call to it, a caller already queued behind the stuck one too, is refused at once (its reply would be read as the old one's) until the late reply comes or `end` ends it. `end` wins over a call it cuts short: that call says so, and the next one goes to another VEGAS this server started, if there is one.

## Safety

The user edits in VEGAS on the same PC, and their VEGAS comes first.

- **Off in every VEGAS the user starts.** VEGAS loads the extension into all of them, so it listens only when its environment has `DODSTUDIO_VEGAS_BRIDGE=1` and a `DODSTUDIO_VEGAS_ROOT` that exists, which only `launch` sets. A VEGAS started from the Start menu, a shortcut or a `.veg` opens no pipe, so nothing can reach the project being edited.
- **One pipe per VEGAS** (`dodstudio-vegas-<pid>`), so bridge VEGAS run beside the user's and beside each other, and a command never reaches a VEGAS it was not meant for: tools go only to a VEGAS this server started unless `use` names another (one started by another session or script is theirs), and when the current one goes, the server says so instead of switching.
- **The work folder.** `save_as`, `render`, `snapshot` and `run_script` refuse paths outside `DODSTUDIO_VEGAS_ROOT`; `open_project` copies a project from elsewhere into `<work folder>\copies` and opens the copy, and `import_edl` takes only EDL text files (`.txt`, `.edl`), so the user's own `.veg` files are never opened or saved. `launch`'s `work_folder` must be inside the server's `DODSTUDIO_VEGAS_ROOT` (or, when that is unset, inside `%TEMP%\dodstudio-vegas`), is never a drive root, and no folder name in it may end in a space or dot. Media is read from anywhere. It is a guard rail, not a sandbox: a script `run_script` runs can write anywhere, VEGAS writes `.sfk` peak files beside the media it imports, and a junction inside the folder leads out.
- **Unseen.** Started minimised and without activation, VEGAS still put its start-up splash and its render progress window (WPF, unowned, shown even in a minimised VEGAS) over the user's full-screen game. So `launch` starts each VEGAS on a desktop of its own (`CreateDesktop` in the user's window station, named `dodstudio-vegas-<server pid>-<n>-<random>`; `mcp/desktops.py`), which is never shown: every window of that VEGAS, its splash, dialogs and any process it starts are there. Measured: no window of a bridge VEGAS visible on the user's desktop through launch, snapshot, renders (CPU and a failing NVENC one) and every dialog test; snapshots still match an Image Sequence render pixel for pixel. Window messages pass only within a desktop, so the dialog answerer, which runs inside VEGAS, still reaches its boxes; a tool outside that sends a VEGAS window messages must move a thread onto that desktop first (`SetThreadDesktop`). The desktop goes when the last process on it has. `minimised: false` starts it on the user's desktop instead, shown without focus, to watch it work.
- **Starting.** `launch` starts `vegas210.exe -SCRIPT:mcp\start_vegas.cs` (a script that does nothing), minimised and without focus. Started with a script, VEGAS opens an empty untitled project instead of its last one (often the user's), and its recent-projects list is left as it was (both measured on build 315). It refuses to start while an `*.autosave.veg` exists whose PID is not a running VEGAS (a crashed session's recovery file), since the new VEGAS would offer to restore it; only VEGAS's default autosave folder is checked, not a custom one set in its preferences. The extension clears the two variables once read, so nothing VEGAS starts inherits them.
- **Ending.** A VEGAS this server started is ended through the process handle it kept from starting it, which also stops Windows giving its PID to another process (the user's next VEGAS) meanwhile. Any other (`end` from the shell, or one reached with `use`) is ended only when it is running VEGAS with a bridge pipe, all checked through the handle that ends it. Never with `vegas.Exit()`, which asks "cancel the background operation?" on screen while peaks build. VEGAS deletes `%LOCALAPPDATA%\VEGAS Pro\21.0\<pid as 8 hex digits>.autosave.veg` only on a clean exit, and a leftover one makes the next VEGAS ask to recover it, so ending deletes that PID's autosave (and `.bak`), and closes a crash's Problem Report box for that PID. A VEGAS being terminated refuses a second `TerminateProcess` with access denied until it has gone (after a long render that took over 2 s), so that is taken as ending; `end` waits up to 30 s for it, and on shutdown one still going then is cleaned up once it has gone, so its autosave never blocks the next launch. On shutdown each VEGAS is waited for on a thread of its own, so however many are stuck, the whole takes at most 75 s (`END_ALL_SECONDS`), not that per VEGAS. Each tool call runs on a thread of its own, so the server always reads stdin: when Claude Code closes it, the server ends every VEGAS it started at once, a stuck call or not (measured: 0.1 s). A server killed outright cannot, so a VEGAS it launched watches it (`extension/OwnerWatch.cs`): the launch passes `DODSTUDIO_VEGAS_OWNER_PID` and `DODSTUDIO_VEGAS_OWNER_START` (its creation time), read and cleared like the other two; the bridge opens a handle to that process (which keeps its PID from being reused) and checks the start time, and when it exits, deletes its own autosave and terminates its own process (measured: gone 0.1 s after the server was killed, autosave removed). VEGAS does not hold its autosave open between saves, and a VEGAS that ends itself leaves it, so it is deleted first. The shell's `launch` passes no owner, since it exits at once.
- **Dialogs** (`extension/DialogAnswerer.cs`), in the bridge VEGAS's own windows only, and only the active modal box: a Windows dialog box that is modal (enabled, its owner disabled, the owner's enabled popup), or has no owner but is the only enabled, shown window of its thread (a modal loop disables the rest); a WinForms form inside its `ShowDialog`, owned or not (`Form.Modal` for VEGAS's own; a script's, from any thread, when the rest of its thread's windows are disabled). Modeless boxes and forms are never touched. A bare `MessageBox(NULL, ...)` on VEGAS's UI thread disables nothing, so it is left alone too and its call runs into its time limit; WinForms' `MessageBox.Show` is answered. Missing media gets "Ignore all missing files and leave them offline" and OK; the first-render "Hint" box OK; "save changes?" No; any other box still open after 4 s Cancel, else No, else OK, else Close, with its text in the reply (a failed NVENC render's "An error occurred while creating the media file" box gets OK). Left alone: a dialog with a progress bar (a render's), VEGAS's offer to restore an autosave, a box still open after 3 presses (reported), and WPF windows (VEGAS's render progress is one, and nothing outside a WPF window tells a modal box from it): a call held up by one runs into its time limit, and `end` ends that VEGAS. English VEGAS only. A script that asks questions with message boxes therefore gets those answers: run it in a VEGAS of your own instead.
- **Errors.** A tool call that fails for any reason returns an error; it never ends the server (which would end its VEGAS). A call past its time limit returns an error too, and its VEGAS refuses calls until it has replied (see Tools). After the current VEGAS goes, bridge tools are refused until `launch` or `use`, so a retried command never lands in another VEGAS. A bridge command that fails part-way is rolled back (its undo block is cancelled).
- Nothing saves in place: `save_as` never overwrites a file it did not write in this session, and `render` and `snapshot` never overwrite a file.

## Snapshots

`snapshot` uses `Vegas.SaveSnapshot`, which renders the frame at the preview's quality and size, so each call sets the preview to Best at full size, takes its frames, and puts the preview and the edit cursor back. The frame is the one a render gives, pixel for pixel (checked against an Image Sequence PNG render of the same frames). A frame takes about 0.1 to 0.5 s (a black gap is fastest, a 2560x1440 ProRes clip scaled down slowest); a call that has to change the preview size waits about 0.3 s more for VEGAS to apply it. The snapshot leaves no undo step and does not mark the project modified (the preview settings are not undoable edits). Each setting goes back on its own, also when the call fails part-way; a call is every frame or none, so a failure deletes the PNGs it had already written. Files are named `<project>_<time>s_<when>_<pid>.png` and claimed with `FileMode.CreateNew`, so two bridge VEGAS sharing a work folder never take each other's names. `folder` may be the work folder itself or any folder inside it.

The MCP result is the reply as text, then one image block per frame. The inline copy is the PNG when it is at most 1 MB (a scaled-down or simple frame), else a JPEG of the same pixels (quality 90, 0.3 MB for a 1280 px frame of a game capture, whose PNG is 2.5 MB), since every image in a conversation is sent again with each later request. A frame wider than 2000 px (`width: 0` on a 4K project) goes inline scaled to 2000 px wide, and says `inline_width`; its PNG on disk keeps the full size. Each frame says `inline_as`, or `not_inline` with why (over 4 MB in one call: the bridge stops encoding inline copies there); `inline: false` sends the text only. From the shell (`call ... snapshot`) the reply shows the paths, not the base64.

## Project detail

Each area is a file of its own in `extension/` (`Keyframes.cs`, `PanCrop.cs`, `TrackMotion.cs`, `Transitions.cs`, `Markers.cs`, `Envelopes.cs`, `EventGroups.cs`), and its tool schemas are in `mcp/detail_tools.py`. Every `set_*` call runs in the command's one undo block, like every other edit, and is rolled back whole when it fails part-way (a bad second keyframe leaves the call before's keyframes; a failed `set_markers` adds nothing; measured). The `get_*` reads and `project_info` run without an undo block, so they leave Edit > Undo and Edit > Redo as they were. Reading a track's Track Motion for the first time makes VEGAS set it up, which fails with `E_UNEXPECTED` outside a block, so a read that fails that way runs again inside an undo block that is always cancelled. The reads leave the project unmodified (measured after a reopen).

Keyframe and point lists share one rule: `mode` "replace" (the default) makes the list exactly what is given, "add" adds to it (replacing one at the same time, within half a millisecond). VEGAS always keeps one keyframe at time 0 (each list's `Clear` leaves it), so given none at 0 it takes the first given keyframe's values, and the value holds from the start until that keyframe. An OFX parameter's "clear" turns animation off, which removes every keyframe; "add" on a parameter not animated yet starts from its static value at 0. Every keyframe and point needs a `time`, a finite number from 0 to the end of what it is on (an event's length, for times from its start); one that is missing, `"NaN"` or out of range fails the call before anything changes. A curve VEGAS's API names `None` is "Hold" both ways, as in VEGAS's own windows.

Units, all measured with `snapshot` on 300 fps colour bars with a frame counter (`t17_project_detail.py`): Event FX keyframes are timeline seconds from the event's start at speed 0.5 and with a take offset; Track FX and Video Output FX keyframes are project seconds. Pan/Crop boxes are source pixels with y down (a box on the top-left quarter shows the counter). Track Motion positions are project pixels from the centre with y up. VEGAS keeps both rotations in radians (`TrackMotionScaleFactors.A` is 57.3); the bridge speaks degrees (180 shows the last bar on the left). Envelope values are VEGAS's own (`min`, `max`, `neutral` come back): Volume 0 to 2 with 1 = 0 dB, Pan -1 to 1, Composite 0 to 1, Velocity a speed (2 shows the media at 1.0 s half a second into the event).

## Presets, many events, comparing projects

`extension/Presets.cs`, `Batch.cs` and `CompareProjects.cs`; schemas in `mcp/edit_tools.py`.

- **Presets** apply by name (`Effect.Preset`, any case; an unknown name is an error that lists the real ones), before any `params`, so `params` change the preset's values. `PlugInNode.Presets` lists them without adding anything. Reading what a preset sets (`read_preset`, and `list_effects` `details`) needs the effect in a chain, so the bridge adds a throwaway copy (an effect on the Video Output FX chain, a transition on the fade of an empty event on a track of its own) inside an undo block that is always cancelled, and removes it before the block ends. Measured: `project_info` with `detail` reads the same before and after, and the project stays unmodified.
- **Saving a preset is left out.** No member of `Effect`, `PlugInNode` or `EffectPresets` in VEGAS's scripting API writes one, and the store is the one the user's own VEGAS reads (a user preset such as Cookie Cutter's saved ones shows in the same list as VEGAS's), so the bridge never writes presets.
- **`apply_to_events`** runs the single-event command for each event the filter picks (`set_event`, `add_effect`, `set_effect_params`, `set_pan_crop`, `set_fade`) with that event's track and index at that moment, so arguments mean what they mean there. Changes run in a fixed order per event (`set_event`, `add_effect`, `set_effect`, `remove_effect`, `pan_crop`, `fade_in`, `fade_out`). Video-only changes skip audio events, `target: "media"` changes each media's Media FX once (add, set and remove alike), and a filter that picks nothing, or a change that fails on any event, changes nothing. A key it does not know, in the filter or in any change, is refused before anything changes (a typo such as `{"trak": 2}` would otherwise pick every event), and so is an empty filter: every event takes `{"all": true}`. The reply's `warnings` name each picked event that now overlaps one the filter did not pick (after a `shift` or a longer `length`), which VEGAS allows and plays as a crossfade.
- **`compare_projects`** matching, said in its reply (`matched_by`): tracks by type and name in order (so a track added in the middle shifts nothing); events within matched tracks by the same file starting within `tolerance` (default 1 ms) from the same media second, then the same file from the same media second (moved), then the same file at the same start (offset changed), then the same file (moved and retrimmed). Each pass pairs the events that may pair in timeline order (as many pairs as fit, then the closest), so the same clip used three times and moved keeps its order, and a clip deleted with another moved onto its place reads as just that. Effects by position in their chain; markers by time and label, then label (moved), in time order the same way. An event whose take now plays another file reads as removed and added. The comparison itself is `mcp/project_compare.py`, run on the bridge's reply (both projects' full detail: every keyframe and point); a `tolerance` that is not a number of seconds is refused before the bridge reads anything. Each `.veg` is read from a copy in `<work folder>\copies`, deleted afterwards. The open project must be saved, since it is reopened from its file afterwards, and **that reopen clears the bridge VEGAS's undo history**: Edit > Undo can no longer take back what came before the compare.
- **Change one thing and render a second** is two calls: `set_effect_params` (or `apply_to_events`) and `render` with `start` and `length: 1` (1.2 s for a 720p60 AVC second, measured). `snapshot` with `times` shows frames without encoding anything.

## Frame Blend by speed (#1051)

VEGAS never tells an OFX effect an event's speed, and an Event FX only sees frames at the project rate (measured in #1051), so Frame Blend works only as a Media FX. `blend_by_speed` does the per-event part at edit time: every event on the track gets its own subclip covering exactly the media it plays, with Frame Blend as that subclip's Media FX and Frames = capture fps / project fps x speed (5 at normal speed on 60 fps, 2 at 2.5x slow, none at 5x slow). It adds the subclip as a new take and keeps the old one, so switching back undoes it. Run it again after changing an event's speed.

## Gotchas found

- Project edits from an extension must sit in an `UndoBlock`; without one every change fails with `E_UNEXPECTED`.
- An EDL opened with `OpenFile` (what File > Open of an EDL does) **replaces** the open project, asking "save changes to Untitled?" when it has any, and `OpenFile` returns before the events exist. `import_edl` clears the dirty state first and pumps messages until the timeline fills (#1303's test).
- `project_info` gives each event its file (`media_path`, a subclip's parent), `offline` and `selected`, and each media `offline`, so an import can be checked for files VEGAS did not find.
- VEGAS fixes its project-matching render templates ("Default Template") the first time templates are listed in a session. Listed before the timeline had video, they stay audio-only until VEGAS restarts, so `render` refuses a template without a video stream.
- Commands run on VEGAS's UI thread from a WinForms timer (`extension/UiQueue.cs`), not `Control.Invoke`: inside an Invoke callback (and `run_script` from one), `OpenProject` of a project with missing media never returns once its box is answered, idle in VEGAS's own wait loop; started from a WM_TIMER, or from a `-SCRIPT` start, it returns in about a second.
- Windows hides the windows a minimised window owns, so a minimised bridge VEGAS's dialogs are hidden. A push button in a hidden dialog ignores `BM_CLICK`, so the answerer sends the dialog the button's `WM_COMMAND` instead (radio buttons still take `BM_CLICK`).
- VEGAS 21's MP4 reader (`dp4_reader`) crashed once in `add_media` of a 300 fps clip while three bridge VEGAS were reading media (`std::terminate` during its own exception); the same call passed every other time. `end` closes the crash's Problem Report box.
- A "Hint" box (OK only) appeared during the very first bridge render and held it until OK was pressed (not seen again in later sessions, so probably shown once per PC). The dialog answerer presses OK on it; that path has not been exercised since.
- Two bridge VEGAS started at once were both ready in 12 s; one on a hidden desktop is ready in 4 to 5 s.
- `Vegas.SaveSnapshot(path, format, time)` works in a minimised VEGAS, but moves the edit cursor to `time`, renders at the preview's quality and size (Draft / Quarter gives a 720p project as 160x90), and throws `ArgumentOutOfRangeException` past the end of the project. Its PNG is RGBA, transparent where no event is, with the colour already multiplied by alpha (a red clip at the middle of a fade to nothing is (127, 12, 0, 127) in an Image Sequence PNG render, and about 120 red in an MP4 render of the same frame), so `snapshot` flattens it onto black by dropping alpha. Multiplying by alpha again, as the bridge did before 0.5, showed that fade at 63. Draft quality renders at half the preview size (a 1280x720 project at Full gives 640x360), so the frame really is taken at Best: from a Draft preview it is the same, pixel for pixel, as from a Best one. On a project with non-square pixels the PNG is in square pixels (720x480 at a pixel aspect of 0.9091 gives 655x480), and an Auto preview size works too; neither waits for the 3 s preview-size limit.
- A take's `Offset` is in stretched (timeline) time: the media second an event starts at is `Offset` x its speed (Offset 1 s at rate 0.5 showed the media's 0.5 s, frame 150 of the counter clip). The bridge's `offset` is media seconds, converted both ways, and set after the speed, since an Offset set at the old speed is clamped to the media's length at that speed. Before 0.5 the bridge passed `offset` through, so at any speed but 1 the event started elsewhere than asked, and `blend_by_speed`'s subclips started at the wrong media second.
- `Project.Undo()` cannot be driven from a `run_script` script: three tries after a `set_pan_crop` did nothing twice and worked once, and a fourth raised "An error occurred while processing the undo buffer ... restart VEGAS Pro", after which the call hung on a second box. Edit > Undo in VEGAS's own window is the way to undo a call.
- Events loop by default (`TrackEvent.Loop` is true on a new event), so `project_info` lists `loop` only when it is off.
- The scripting API has no event colour, and gives audio events no envelopes (`AudioEvent` has no `Envelopes`; a video event can take only Velocity).
- VEGAS lists each effect under several folders of its FX tree, as separate nodes with one id (Frame Blend under four, plus the top of the tree), so a plain walk lists it five times; `list_effects` lists it once with its `categories`.
- A detached `new Effect(plugIn)` throws `NullReferenceException` on every property (`IsOFX`, `OFXEffect`, `Presets`) until it is in a chain or on a fade.
- Setting Track Motion's position moved the track's 2D shadow and glow keyframes by the same amount (`compare_projects` showed shadow x 18 to 118 and glow x 0 to 100 after `set_track_motion` x 100).
- Legacy DirectX video effects could not be added at all: `Effects.AddEffect` failed with `E_FAIL` for each of the 12 tried (Threshold, Film Grain, TV Simulator, ...), so `add_effect` refuses them by name ("legacy DirectX effects can't be added"). The FX packages `list_effects` shows (no id) are preset chains, not plug-ins.
- A Pan envelope on an audio track comes back from a saved project with PanY, PanSmoothness and PanCenter envelopes beside it (neutral points); Volume and Pan keep their points.
- Markers, regions and command markers stay in time order: moving one past another changes both indices, so `set_markers` reads every index from the lists as they were before the call.
- `Project.AddVideoTrack()` inserts the new track at index 0, moving every other track down one; `AddAudioTrack()` appends. `new VideoTrack(project, project.Tracks.Count, name)` then `Tracks.Add` appends, which `add_media` does.
- An Image Sequence render to `f.png` writes `f_000000.png`, `f_000001.png` and on, never `f.png`; `render` lists those and refuses a path whose numbered files exist.
- VEGAS runs scripts in their own AppDomain ("Script Domain"; the extension is in "VEGAS Domain"), so `Control.FromHandle` cannot see a script's WinForms forms. A WinForms button clicks only when the mouse is over it at mouse-up, so `BM_CLICK` misses in a hidden form, but its form turns a `WM_COMMAND` (BN_CLICKED) from it back into a click from any AppDomain, which the dialog answerer sends.
- Bad media (a text file named `.mp4`, an `.xyz`) makes `add_media` fail with `E_FAIL` and no box; a garbage `.veg` makes `OpenProject` return false, no box.
- VEGAS writes its autosave a few seconds after the first edit, not at start, and does not hold it open.
- Every VEGAS keeps its Hub's WebView2 data in one folder, `%LOCALAPPDATA%\VEGAS Pro\21.0\WebView2`, and starts WebView2 (six `msedgewebview2.exe`) within seconds of starting, a `-SCRIPT` start on a hidden desktop too. WebView2 refuses a folder another browser process holds with other settings, so with a bridge VEGAS holding it, the user's VEGAS opened beside it showed "VEGAS Hub: WebView2 failed initialization ... The requested resource is in use (0x800700AA)" on their screen. `launch` gives each bridge VEGAS a folder of its own through `WEBVIEW2_USER_DATA_FOLDER`, which WebView2 takes over the one VEGAS asks for (measured: every one of its WebView2 processes runs with `--user-data-dir` in it, none with the user's), and removes it when that VEGAS has ended; a later launch removes the ones a killed server left, touching only folders named as `launch` names them (`vegas-<server PID>-<random>`) and leaving one whose PID file is not written yet for ten minutes (`mcp/webview_folders.py`).
- The preview settings (`Project.Preview`) are not undoable edits: changing them adds no undo step and leaves `IsModified` alone. From an extension the quality still needs an `UndoBlock` (`E_UNEXPECTED` without one); the size does not. A new quality applies at once, but a new preview size only after VEGAS's own message loop has run, not inside a command and not with `Application.DoEvents`, so `snapshot` takes its frames in a later step of the same command (`LaterStep` in `extension/UiQueue.cs`).
